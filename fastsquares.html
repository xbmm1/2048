Compare Performance Over Time: Fast Inverse Sqrt vs Normal Math.sqrt

Explanations

At first glance, this might seem surprising because the "fast inverse square root" algorithm was famous for being faster in older hardware and specific contexts (like in Quake III Arena back in the late 90s). However, in modern JavaScript engines and on modern CPUs, the situation is quite different:

  • Math.sqrt is highly optimized in modern JavaScript engines and hardware. Modern CPUs have dedicated floating-point instructions for square root that are extremely fast and well-optimized by JavaScript JIT compilers.
  • The "fast inverse sqrt" algorithm involves bit-level manipulation and conversions between float and integer representations (ArrayBuffer, Float32Array, Uint32Array), which add overhead in JavaScript. These operations are relatively expensive compared to a direct hardware sqrt instruction.
  • Memory operations and type coercions inside the fast inverse sqrt function slow it down, particularly because JavaScript doesn't have native pointers or direct memory access like C/C++.
  • The fast inverse sqrt algorithm is designed to approximate inverse square root (1 / sqrt(x)), and your implementation then multiplies by x to get sqrt(x). This two-step approach adds extra operations compared to calling Math.sqrt(x) once.
  • Modern engines can vectorize or optimize Math.sqrt calls better than complex manual implementations in JS.

In summary: The fast inverse sqrt algorithm was a clever trick for its time and platform but does not outperform native hardware-accelerated Math.sqrt in modern JavaScript environments. That's why you see normal Math.sqrt calculating roughly 4 times more square roots in the same time.
