# Dungeon Crawler — Wilson Maze + A\*

A tiny **DOOM-style** 3D dungeon crawler that runs entirely in the browser with
plain HTML/CSS/JavaScript (no build step, no dependencies).
https://xbmm1.github.io/2048/Project_Root/doom-crawler/doom2/index.html
Open `index.html` in any modern browser and play.

## Highlights

- **Raycasting renderer** (`js/raycaster.js`) — classic DOOM-style pseudo-3D.
  One DDA ray per screen column for walls, plus billboarded sprites with a
  per-column depth buffer so enemies are correctly hidden behind walls.
- **Wilson's algorithm levels** (`js/maze.js`) — each floor is a perfect maze
  generated by a loop-erased random walk (a Uniform Spanning Tree), then
  expanded into a wall/floor tile grid.
- **A\* enemy AI** (`js/astar.js`, used in `js/game.js`) — monsters chase you
  through the maze using A\* over the tile grid, re-planning periodically.

## Controls

| Action | Keys |
| --- | --- |
| Move | `W` `A` `S` `D` |
| Turn | `←` `→` or mouse (click canvas to lock pointer) |
| Shoot | `Space` or click |
| Toggle A\* path overlay on minimap | `M` |

## Goal

Each floor, collect the required **keys**, then reach the glowing **exit
portal** to descend. Enemies get faster and more numerous the deeper you go.
Find health packs to survive. See how many floors you can clear.

# How It Works (Detailed)

This section explains every major system in the game, top to bottom: how levels
are generated, how the 3D view is drawn, how enemies think, and how the math
actually performs.

## 1. Level generation — Wilson's algorithm (`js/maze.js`)

Each floor is a **perfect maze**: a grid where every cell is reachable and there
is exactly one path between any two cells (no loops, no isolated areas).

### Why Wilson's algorithm?

Many maze algorithms (recursive backtracker, Prim's) are biased — they tend to
produce mazes with characteristic textures (long corridors, lots of short dead
ends, etc.). Wilson's algorithm is special because it generates a **Uniform
Spanning Tree**: every possible maze of that size is *equally likely*. The
result is unbiased, varied levels.

### The loop-erased random walk

The core idea:

1. Pick one random cell and mark it as part of the maze.
2. Pick any cell **not** yet in the maze. Do a **random walk** from it, stepping
   to random neighbours, until you bump into a cell that *is* already in the maze.
3. While walking, if you cross your own path and form a loop, that loop is
   **erased** — we only keep the most recent direction chosen from each cell.
   In the code this is just `path.set(key(cx, cy), d)`: overwriting the previous
   choice for a cell automatically erases any loop through it.
4. Once the walk reaches the maze, **carve** the (now loop-free) path into the
   maze, marking every cell on it as visited.
5. Repeat until every cell has been absorbed into the maze.

```js
// Loop-erased random walk: keep overwriting each cell's chosen direction
while (!visited.has(key(cx, cy))) {
  // pick a random in-bounds direction d -> (nx, ny)
  path.set(key(cx, cy), d); // overwriting == automatic loop erasure
  cx = nx; cy = ny;
}
```

### From cells to walls (`toTiles`)

The logical maze stores, per cell, which of its four neighbours it connects to.
That `cols × rows` grid of connections is then expanded into a
`(cols*2+1) × (rows*2+1)` **tile grid** where `1 = wall` and `0 = floor`:

- Odd coordinates `(2x+1, 2y+1)` are cell centres → always floor.
- The tile *between* two connected cells is carved to floor; everything else
  stays a wall.

This tile grid is the single source of truth the renderer, collision, and A\*
all walk through.

## 2. The 3D view — raycasting (`js/raycaster.js`)

The game is not true 3D. It uses **raycasting**, the same technique as Wolfenstein
3D / DOOM: the world is a flat 2D grid, but we render it as if you're standing
inside it.

### Casting walls with DDA

For each of the 960 vertical screen columns we:

1. Compute a ray direction fanned across the **field of view** (`FOV = 60°`).
2. March that ray through the tile grid using **DDA** (Digital Differential
   Analysis) — a grid-stepping algorithm that jumps exactly from one grid line
   to the next, so it only tests the cells the ray actually crosses. This is
   much faster than sampling fixed-size steps.
3. Stop at the first wall tile hit.

### Fixing the fisheye + sizing the slice

We use the **perpendicular distance** to the wall, not the raw ray length:

```js
const perpDist = side === 0 ? sideDistX - deltaDistX : sideDistY - deltaDistY;
```

Using the straight-line (Euclidean) distance would bow the walls outward like a
fisheye lens. Projecting onto the camera direction keeps walls straight. The
wall slice height is then simply `H / perpDist` — closer walls are taller.

### Shading and the depth buffer

- **Shading:** slices darken with distance (`1 - perpDist / 16`) and walls
  facing sideways are dimmed to `0.68` so corners read clearly — a cheap fake
  for directional lighting.
- **Depth buffer (`zbuffer`):** the `perpDist` of every column is stored. This
  is what lets sprites hide correctly behind walls (see below).

### Billboarded sprites

Enemies, the exit portal, keys, and health packs are **billboards** — flat
images always turned to face the camera. To draw one:

1. Transform its world position into camera space using the inverse of the
   camera/plane matrix (`invDet * ...`). `transformY` is its depth.
2. Project it to a screen X and a size of `H / transformY`.
3. For each of its columns, compare the sprite's depth against `zbuffer[x]`. If
   a wall in that column is closer, **skip the column** — that's the occlusion.

```js
for (let x = x0; x < x1; x++) {
  if (depth >= zbuffer[x]) continue; // a wall is in front → don't draw
  paintColumn(...);
}
```

Sprites are also sorted far → near so nearer ones paint over farther ones.

## 3. Enemy AI — A\* pathfinding (`js/astar.js` + `js/game.js`)

Enemies chase the player through the maze using **A\* search** over the tile
grid.

### The algorithm

A\* finds the shortest path while exploring as few cells as possible by ranking
candidates by:

$$ f(n) = g(n) + h(n) $$

- `g(n)` — actual steps taken from the enemy to cell `n`.
- `h(n)` — the **heuristic** estimate from `n` to the player. We use **Manhattan
  distance** (`|dx| + |dy|`), which is admissible for 4-directional movement
  (it never overestimates), so A\* is guaranteed to find an optimal path.

### The open set is a binary min-heap

Pulling the lowest-`f` candidate is the inner-loop hot path, so the open set is a
hand-written **binary min-heap** (`MinHeap`) giving `O(log n)` push/pop instead
of repeatedly scanning an array. Movement is restricted to the 4 cardinal
directions so monsters never clip diagonally through a wall corner.

### Re-planning (keeping it cheap)

Running A\* for every enemy every frame would be wasteful. Instead each enemy
re-plans only every ~350–600 ms (`e.repathAt`), then smoothly walks toward the
next waypoint between re-plans:

```js
if (now >= e.repathAt || !e.path) {
  e.path = AStar.find(state.tiles, ex, ey, px, py);
  e.pathIndex = 1;                       // skip the tile it's standing on
  e.repathAt = now + 350 + Math.random() * 250;
}
```

Press **`M`** in-game to draw each enemy's current A\* path on the minimap.

## 4. Game loop, movement, and combat (`js/game.js`)

- **Game loop:** a `requestAnimationFrame` loop computes a clamped delta-time
  `dt`, updates the player and enemies, renders the 3D view, then draws the
  minimap.
- **Collision:** movement is **axis-separated** — we try the X move and the Y
  move independently so you *slide* along walls instead of sticking.
- **Shooting:** hitscan. We find the nearest living enemy inside a small aiming
  cone in front of the player and confirm nothing is in the way with a
  `lineClear` ray march before applying damage and knockback.
- **Progression:** the exit is placed on the floor tile **farthest** from spawn
  (found by running A\* to sampled tiles and keeping the longest path). Collect
  the required keys, reach the portal, descend. Mazes grow and enemies speed up
  each floor.

## 5. A note on math performance (and "fast inverse sqrt")

A reasonable question: *would using the famous Quake III "fast inverse square
root" trick speed this up?* For this game, **no — it would make it slower.**

### Why native `sqrt` wins today

- Modern CPUs have a **dedicated hardware square-root instruction**, and JS
  engines compile `Math.sqrt` / `Math.hypot` straight down to it.
- The fast-inverse-sqrt trick needs `ArrayBuffer` + typed-array views, bit
  shifts, the magic constant `0x5f3759df`, and a Newton refinement step. In
  JavaScript that is **more work and more memory traffic** than the single
  native instruction it replaces — *and* it only returns an approximation
  (~0.17% error after one Newton step).

The repo's own [`fastSquaredemo.html`](../fastSquaredemo.html) benchmarks this:
native `Math.sqrt` performs roughly **4× more** operations in the same time.

### What the game actually does instead (the real optimization)

The genuine win isn't a fancier sqrt — it's **not computing sqrt at all** when
you only need to compare distances. Squaring is monotonic, so to ask "is A
closer than B?" you can compare squared distances and skip the root entirely.
That's exactly what the `dist2` helper does:

```js
const dist2 = (a, b) => (a.x - b.x) ** 2 + (a.y - b.y) ** 2;
// e.g. proximity checks compare against a squared threshold:
if (dist2(e, p) < 0.55 && e.cooldown <= 0) { /* attack */ }
```

`Math.hypot` is used only in the few places that need a **real length** (to
normalize a direction vector for movement/knockback, or to count ray-march
steps). Those run at most a few hundred times per frame and are negligible next
to the ~960 wall rays the raycaster casts — none of which use `sqrt` in their
hot path.

**Takeaway:** the meaningful performance levers here are fewer rays / smaller
render buffer, throttled A\* re-planning (already done), and using squared
distances where the actual length isn't needed — not swapping in a 1999-era
sqrt approximation.
